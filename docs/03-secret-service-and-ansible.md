# 3. Сервис управления секретами и Ansible

[Главная страница](../README.md)

## Назначение сервиса

В составе проекта я реализовал отдельный собственный [secret manage service](https://github.com/A-R-M-O-R/Secret-manage-service). Я разместил его на VM `app-secrets` и использовал для хранения паролей управления узлами. Этот же сервис включил в тесты подбора пароля API и перебора путей секретов.

Репозиторий приложения содержит готовую реализацию. В этой главе я описываю его использование в SOC-лаборатории и связь с Ansible.

## Какие секреты я храню

| Узел             | Путь                                          | Назначение               |
| ---------------- | --------------------------------------------- | ------------------------ |
| `app-secrets`    | `ansible/hosts/app-secrets/ssh/password`      | Пароль SSH для Ansible   |
| `soc-wazuh`      | `ansible/hosts/soc-wazuh/ssh/password`        | Пароль SSH для Ansible   |
| `soar-ir`        | `ansible/hosts/soar-ir/ssh/password`          | Пароль SSH для Ansible   |
| `win10-endpoint` | `ansible/hosts/win10-endpoint/winrm/password` | Пароль WinRM для Ansible |

## Устройство приложения

Я использовал три контейнера: Nginx, FastAPI и PostgreSQL. Nginx принимает запросы на HTTP/8080 и HTTPS/8443, FastAPI обрабатывает API, PostgreSQL хранит данные.

Для пользователя предусмотрен вход по логину и паролю с получением JWT. Для автоматизации я использовал сервисную учётную запись с `X-API-Key`. Доступ к конкретному секрету определяется отдельным правом.

Значения секретов шифруются Fernet. Мастер-ключ подключается отдельно от записей БД. Приложение поддерживает версии секретов, чтение, мягкое удаление, выдачу прав и журналирование операций.

## Как Ansible получает пароль

Я подключил [lookup-плагин](../ansible/lookup_plugins/secret_service.py), который обращается к `/api/v1/secrets/{path}`.

1. В переменных узла я указываю путь секрета.
2. Плагин отправляет запрос с ключом сервисной учётной записи.
3. Сервис проверяет ключ и право чтения.
4. Плагин возвращает пароль в `ansible_password`.
5. Ansible использует его для SSH или WinRM.

Для Linux пароль также подставляется в `ansible_become_password`. На Windows я использую учётную запись `ansible` и отключённый `become`.

Адрес сервиса и параметры запроса я храню в общих переменных. Ключ сервисной учётной записи — в локальном `.env`. В выбранной лабораторной конфигурации проверка TLS в плагине отключена.

## Подготовка доступа

Для создания секретов и прав я использовал [create_ansible_secret.py](../ansible/create_ansible_secret.py). Скрипт позволяет создать сервисную учётную запись либо использовать существующую, создать или обновить значения, выдать чтение и проверить доступ.

При настройке я выбираю четыре пути своей лаборатории. Предложения скрипта для `win-server` и `ndr-sensor` пропускаю: этих узлов в итоговой архитектуре нет.

## События приложения в Wazuh

Для обнаружения API-атак я подключил JSON-журнал Nginx:

`/var/log/secret-service/nginx/access_wazuh.json`

Из него получаю IP, метод, путь, код ответа и контекст запроса. Отдельные журналы аудита приложения и PostgreSQL в Wazuh я не собираю.

## Файлы автоматизации

В [каталоге Ansible](../ansible/README.md) я разместил:

- `inventory/hosts.yml` с четырьмя узлами и группами.
- `lookup_plugins/secret_service.py` для получения паролей.
- `create_ansible_secret.py` для подготовки секретов и прав.
- `ansible.cfg` и `requirements.yml`.

Я использовал готовые роли и код как основу. Практическую работу сосредоточил на развёртывании, настройке и проверке интеграций.
